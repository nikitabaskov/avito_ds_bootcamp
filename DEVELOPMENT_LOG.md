## Данные и протокол оценки

Задача — вернуть до 50 идентификаторов объявлений на запрос. Метрика — macro Recall@50: для каждого запроса считается доля найденных известных позитивов, затем результат усредняется с одинаковым весом запросов.

```text
Recall@K = mean_q(|top_K(q) ∩ positives(q)| / |positives(q)|)
```

| Данные | Объём | Назначение |
|---|---:|---|
| `train.parquet` | 497 673 положительные пары | Локальная валидация и будущая обучающая выборка |
| `benchmark_queries.parquet` | 2 452 запроса без ответов | Финальный инференс |
| `benchmark_items.parquet` | 189 212 объявлений | Единственный допустимый корпус финального поиска |

Локальная оценка использует отдельный корпус: все 344 825 уникальных объявлений из train. Наличие dev/test-объявлений в поисковом индексе необходимо, чтобы их можно было найти; их положительные связи с запросами не должны использоваться для обучения. Сами метки — наблюдавшиеся выборы пользователей, а не исчерпывающая экспертная разметка: отсутствие выбора не доказывает нерелевантность объявления.

Текущий протокол:

- Текст нормализуется: нижний регистр, `ё → е`, удаление лишних пробелов.
- Разбиение train/dev/test определяется SHA-256 от нормализованного текста и `seed=42`, в пропорции 80/10/10. Один текст не попадает в разные части.
- Контекст запроса — нормализованный текст и четыре остальных поля `search_*`. Позитивы — множество уникальных `item_id` этого контекста.
- В `eval_dev` и `eval_test` выбрано по 2 452 различных текста, по одному контексту на текст.
- Конфигурации сравниваются на dev. Test предназначен для однократной финальной проверки выбранного решения.

| Часть | Уникальные нормализованные тексты | Контексты |
|---|---:|---:|
| Train | 58 956 | 275 892 |
| Dev | 7 458 | 40 405 |
| Test | 7 459 | 38 008 |

**Обнаруженное ограничение выборки.** `sample_eval_queries` сначала сортирует контексты по хешу, затем оставляет первый контекст каждого текста и первые 2 452 текста. Поэтому у текста с большим числом контекстов больше шансов попасть в выборку. При проверке среднее число контекстов на текст составило 13,37 среди выбранных текстов против 5,42 среди всех текстов dev. Равный вес уже выбранных запросов не устраняет это смещение. Исправление ещё не внесено: нужно сначала независимо выбрать тексты по хешу текста, затем контекст внутри каждого текста и пересчитать сравнение моделей. Все метрики ниже относятся к **текущей версии выборки**.

Локальная оценка также отличается от benchmark размером корпуса и распределением запросов. Пустые фильтры встречаются у 43% запросов dev против 63% benchmark; категория `0` представлена в dev всего двумя запросами против 222 в benchmark. Эти срезы не позволяют обещать тот же результат на скрытой разметке.

**Принятое решение:** BM25 с русской морфологией и E5; глобальные и локальные кандидаты; объединение через RRF. Это исходные гипотезы архитектуры, их полезность проверяется в DEV-003 и DEV-004.

Примеры ошибок в ноутбуке отобраны для иллюстрации, не для оценки их частоты. Иерархия `location_id` и точный смысл цены `−1` не документированы. Совпадение или различие кодов локации нельзя безусловно трактовать как один или разные города.

## DEV-003 — Локальная валидация и BM25

**Гипотеза:** лексический поиск по полному тексту даст базовый уровень качества; усиление заголовка и текстовые фильтры помогут точнее отбирать объявления.

Реализованы описанный выше split, macro Recall@K и BM25S: метод `lucene`, `k1=1.5`, `b=0.75`, Snowball-стеммер `russian` через PyStemmer, стоп-слова `ru`. Документ содержит заголовок, параметры и описание. Вес заголовка приближён повторением его текста. Кандидаты с нулевым score исключаются.

Все варианты ниже используют глобальный поиск без локации, одну dev-выборку из 2 452 запросов и корпус из 344 825 объявлений.

| Вариант BM25 | R@50 | R@100 | R@300 | R@1000 |
|---|---:|---:|---:|---:|
| Заголовок ×1 | 0,3110 | 0,4051 | 0,5705 | 0,7529 |
| Заголовок ×3 | 0,3345 | 0,4243 | 0,5844 | 0,7685 |
| Заголовок ×1 + фильтры запроса | 0,3148 | 0,4108 | 0,5823 | 0,7680 |
| **Заголовок ×3 + фильтры запроса** | **0,3398** | **0,4288** | **0,5889** | **0,7764** |

**Решение:** оставить заголовок ×3 и добавление фильтров. Совместный прирост к исходному BM25 — 0,0288, или 2,88 процентного пункта Recall@50. Большой разрыв между R@50 и R@1000 показывает, что часть известных позитивов находится глубоко в выдаче.

На лучшем варианте R@50 для запросов без фильтров — 0,3912, с фильтрами — 0,3005. Это сравнение разных групп запросов; само по себе оно не доказывает, что добавлять фильтры вредно. Такое решение проверяется сравнением вариантов на одних запросах в таблице выше.

Дополнительно в исходном журнале зафиксирована замена Snowball на лемматизацию pymorphy3: R@50 = 0,3423 против 0,3398, парный bootstrap CI95 для разности [−0,0034; +0,0084], построение индекса 104 с вместо 68 с. Убедительного выигрыша не установлено, оставлен Snowball. Отдельный отчёт этой диагностики среди проверенных JSON не найден; результат сохранён как историческая запись.

**Ресурсы исходного запуска:** индекс 65–68 с; top-1000 для 2 452 запросов около 11 с на 30 потоках CPU; пиковая RSS около 6,7 ГБ. Подготовка split — около 6 с и 5,1 ГБ RSS. Это замеры отдельных запусков, не гарантия времени на другой машине.

**Ограничения:** параметры `k1/b` не подбирались; повтор заголовка не равнозначен полноценному полевому BM25; география пока не учитывается. Следующим этапом проверены E5 и локальные кандидаты.

**Код в текущей структуре:** [данные и split](src/candgen/core/data.py), [метрика](src/candgen/core/metrics.py), [BM25](src/candgen/core/bm25.py), [запуск оценки](src/candgen/scripts/evaluate_bm25.py).

## DEV-004 — Семантический поиск и локальные кандидаты

**Гипотезы:** E5 дополнит лексическое совпадение; отдельные локальные списки помогут учитывать контекст запроса, сохраняя возможность найти объявления с другим `location_id`.

### Конфигурация

- E5: `intfloat/multilingual-e5-base`, ревизия `d128750597153bb5987e10b1c3493a34e5a4502a`, без дообучения.
- Документ: `passage: ` + заголовок + первые 500 символов параметров + описание; максимум 512 токенов. Запрос: `query: ` + текст + фильтры.
- Эмбеддинги нормализованы. Энкодер на GPU работает в fp16; сохранённые векторы загружаются в float32 для точного поиска скалярным произведением блоками.
- Глобальный список ищется по всему корпусу, локальный — только при `item_location_id == search_location_id`.
- От каждого канала берутся до 300 глобальных и до 200 локальных кандидатов: суммарно не более 1 000 до дедупликации. Это внутренний бюджет решения; финальный ответ ограничен 50 объявлениями.
- RRF складывает `1 / (60 + rank)` по четырём спискам, ранги начинаются с 1. При равных итоговых баллах порядок определяется `item_id`.

Код разделён на [core](src/candgen/core/) с логикой поиска и [scripts](src/candgen/scripts/) с запуском, кэшированием и отчётами. Выдачи сохраняются в `data/artifacts/runs/`: global до 1 000, local до 500 кандидатов.

### Результаты

Все значения получены на том же dev, что и DEV-003. «Полнота пула» — macro recall по объединению кандидатов до отбора 50; «размер пула» — среднее число уникальных кандидатов на запрос. В таблице каждый пул ограничен 1 000, поэтому полнота совпадает с полем `recall.@1000` отчёта.

| Вариант | R@50 | R@100 | R@300 | Полнота пула | Размер пула |
|---|---:|---:|---:|---:|---:|
| BM25 global, до 1 000 | 0,3398 | 0,4288 | 0,5889 | 0,7764 | 983 |
| E5 global, до 1 000 | 0,2426 | 0,3122 | 0,4602 | 0,6517 | 1 000 |
| RRF: BM25 + E5, global 300 | 0,3268 | 0,4412 | 0,5921 | 0,6754 | 509 |
| RRF: BM25, global 300 + local 200 | 0,7578 | 0,8250 | 0,8841 | 0,8938 | 429 |
| RRF: E5, global 300 + local 200 | 0,6604 | 0,7416 | 0,8420 | 0,8557 | 454 |
| **RRF: BM25 + E5, global 300 + local 200** | **0,7912** | **0,8515** | **0,9057** | **0,9368** | **731** |

**Вывод:** основной прирост даёт учёт локации. Добавление E5 к BM25 с глобальными и локальными списками даёт ещё **0,0334**, или **3,34 процентного пункта R@50**. В проверенной конфигурации глобальный гибрид без локальных списков уступает BM25. Это не означает, что E5 полезен только с географией при любых настройках.

Самостоятельные локальные каналы: BM25 R@50 = 0,6952, E5 = 0,6483. Пустая локальная выдача встречается у 397 и 380 запросов соответственно, что дополнительно обосновывает сохранение глобальных списков.

### Проверка альтернатив

| Изменение относительно полного гибрида | R@50 | Разность | Решение |
|---|---:|---:|---|
| Убрать E5 | 0,7578 | −0,0334 | Сохранить E5 |
| Убрать фильтры из запроса E5 | 0,7904 | −0,0009 | Сохранить текущую конфигурацию |
| Global 100 + local 400 | 0,7874 | −0,0039 | Пул меньше (606), убедительного преимущества нет |
| Global 500 + local 300 | 0,7915 | +0,0002 | Пул в среднем 1 155, выходит за внутренний бюджет |
| RRF `k=20` вместо 60 | 0,7835 | −0,0077 | Оставить `k=60` |

В исходном журнале для первых трёх изменений зафиксирован парный bootstrap по запросам, 5 000 повторов: CI95 разности соответственно [−0,0449; −0,0222], [−0,0080; +0,0063], [−0,0094; +0,0018]. Интервалы не входят в сохранённые JSON-отчёты и при редактуре не пересчитывались. Они характеризуют текущую dev-выборку и не устраняют её смещение.

Для варианта global 500 + local 300 поле `recall.@1000` ограничивает выдачу первой тысячей, а `mean_pool_size` учитывает весь пул. В таком отчёте R@1000 нельзя подписывать как полноту всего пула.

| Срез | Число запросов | R@50 |
|---|---:|---:|
| Пустые фильтры | 1 062 | 0,7927 |
| Заданы фильтры | 1 390 | 0,7901 |
| Одно слово | 163 | 0,7194 |
| Два слова | 882 | 0,7963 |
| Три слова | 775 | 0,8033 |
| Четыре слова и более | 632 | 0,7880 |

В последнем срезе знаменатель включает только позитивы, отсутствующие среди взаимодействий train-части; число запросов — количество контекстов, содержащих хотя бы один такой позитив. Эти объявления присутствуют в локальном поисковом корпусе. Срез не равнозначен оценке на всём новом корпусе benchmark.

Разрыв между запросами с фильтрами и без них, наблюдавшийся у BM25 global, почти исчез. Среди рассмотренных групп по длине запроса самые трудные — однословные запросы. По категории `0` делать выводы нельзя: в dev только два запроса.

### Где остаются потери

На текущем dev **0,0632** macro recall теряется до попадания в пул, ещё **0,1455** — между пулом и top-50. Эти значения округлены независимо. Разрыв показывает потенциал улучшения отбора, но не является обещанием прироста от CatBoost.

В исходном журнале также сохранены разовые диагностики:

- В top-50 89,5% кандидатов и 96,0% найденных позитивов обнаружены обоими каналами. Среди позитивов пула 8,6% найдены только BM25 и 4,5% только E5. Это основание проверить отбор по отдельным рангам и score каналов.
- Среди 2 662 положительных пар dev 625 имеют другой `location_id`. Для них найдены 76,0% позитивов в пуле и 41,4% в top-50; для 2 037 пар с совпадением — 98,6% и 89,7%. На несовпадающие локации приходится около 84% пропущенных при поиске позитивов. Это доли пар, их нельзя напрямую сравнивать с macro recall по запросам.
- Медиана числа объявлений с совпадающей локацией: dev 2 103, benchmark 1 638; доля запросов без таких объявлений — 15,5% и 17,4%. Случайный выбор 50 локальных объявлений дал R@50 = 0,0507. Эти наблюдения поддерживают полезность сочетания текста и локации, но не доказывают перенос качества на benchmark.

Эти диагностики сохранены из предыдущей версии журнала; отдельные воспроизводимые отчёты для них при проверке не обнаружены. Основная таблица качества, конфигурации и срезы сверены с JSON-отчётами.

### Ресурсы и ограничения

Метаданные эмбеддингов подтверждают: 344 825 документов закодированы за 836 с, примерно 410 документов/с при batch 64; пиковая память GPU по `max_memory_allocated` — 1,4 ГБ. Это память, учитываемая PyTorch, а не полное потребление GPU. На выборке 5 000 документов 35,54% превышают 512 токенов и обрезаются.

Исходный журнал содержит замеры отдельных запусков: dense global около 9 с, local 0,3 с; BM25 — индекс 65 с, global 72 с, local 20 с; пиковая RSS 7,4 ГБ. Отчёт выбранного гибрида сейчас отражает запуск с готовыми кэшами, поэтому его `timings` не описывает полный инференс. Время BM25 также отличается от DEV-003; без одинаковых условий запуска эти числа не сравниваются как ускорение или замедление.

Дополнительная диагностика обрезки текста дала около 35,1% длинных документов, медиану длины 387 токенов, p90 941, максимум 2 886. Заголовок и ограниченные параметры помещались; по этой выборке отбрасывалось около 25,2% токенов, у обрезанных документов оставалось в медиане 61% описания. Значение 35,54% из `meta.json` используется как основной воспроизводимый замер; подробная диагностика отдельно не воспроизведена.

Увеличение лимита параметров до 1 000 символов и кодирование объявления несколькими фрагментами оставлены гипотезами. Они требуют пересчёта эмбеддингов; эффект на качество и память не измерен. Пока более обоснован следующий эксперимент с отбором из уже найденного пула.

Команды приведены для текущей структуры пакета после DEV-004. Исходные Parquet должны находиться в `data/input/`. Для первой подготовки модели нужны её веса; вычисления выполняются локально.

Подготовка эмбеддингов — отдельный ресурсоёмкий шаг, который не нужно повторять для каждого варианта RRF. Но после изменения данных или обработки текстов старые артефакты следует инвалидировать: проверка кэша выдач сейчас опирается на ID запросов и имя конфигурации, а проверка эмбеддингов — на порядок ID объявлений. Это не полный контроль содержимого корпуса, текстов и всех настроек модели.

Источники результатов в локальной рабочей копии:

- `data/artifacts/split/meta.json` — размеры частей и корпуса.
- `data/artifacts/experiments/bm25_dev_*.json` — варианты BM25.
- `data/artifacts/experiments/rrf_dev_*.json` — гибриды, срезы и конфигурации.
- `data/artifacts/embeddings/split_multilingual-e5-base_len512_p500/meta.json` — параметры и ресурсы кодирования корпуса.

`data/` исключён из Git: проверяющий не получит эти отчёты при клонировании. Перед сдачей нужно вынести компактные отчёты выбранных экспериментов в отслеживаемый каталог и дополнить README инструкцией полного запуска. Сейчас README содержит только название задания.

При проверке состояния 17 сентября: основные таблицы сверены с сохранёнными JSON, прочитаны код метрики и формирования выборки, **`uv run pytest -q`: 17 passed**. Повторное кодирование корпуса, полный запуск поиска и независимая оценка test в рамках редактирования журнала не выполнялись. Прохождение unit-тестов не подтверждает готовность `answer.csv`.

## Следующие шаги и критерии готовности

1. **Исправить выборку dev/test.** Выбирать тексты независимо от числа контекстов. Повторить на новом dev сравнение BM25 global, BM25 global + local и полного гибрида; явно отделить новые метрики от приведённых выше. Test пока не использовать для настройки.
2. **Завершить финальный инференс.** Построить поиск по `benchmark_items`, обработать все 2 452 benchmark-запроса, сформировать `answer.csv` и проверить колонки, набор `query_id`, принадлежность `item_id` корпусу, уникальность и лимит 50. Умение подготовить benchmark-эмбеддинги ещё не означает готовности этого пути.
3. **Проверить обучаемый отбор.** Обучать CatBoost только на train-контекстах и кандидатах, полученных тем же поиском; использовать ранги и score каналов, совпадение локации и простые признаки текста. Не использовать dev/test-позитивы для обучения или искусственного пополнения оценочного пула. Ненаблюдавшиеся пары — приближённые негативы. Сохранить модель только при подтверждённом выигрыше над RRF.
4. **Зафиксировать результат для сдачи.** После выбора конфигурации один раз оценить её на test; сохранить компактные отчёты, версии и команды полного запуска; проверить воспроизводимость итогового файла.

Каждый итоговый файл планируется сохранять отдельно: `data/output/NNN_YYYYMMDD-HHMMSS_<tag>/answer.csv` и `meta.json` с конфигурацией, версией локальной оценки, commit и SHA-256 ответа. Существующие папки не перезаписываются. Это соглашение для будущего экспорта, а не уже реализованный механизм.
