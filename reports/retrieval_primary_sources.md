# Первичные источники: рост Recall@50

Дата проверки: 2026-09-18. Это обоснование экспериментов, а не результаты их запуска. Код и модели не менялись. Числа текущего проекта анализируются в основном отчёте; внешние benchmark-результаты не дают прогноза прироста на объявлениях Avito.

## 1. Согласовать обучение ранкера с метрикой

Обычный `YetiRank` означает `mode=Classic`, с `decay=0.85`. При метках в диапазоне `[0,1]` автоматически выводимая метрика — PFound; это не утверждение о точном равенстве функции оптимизации PFound. Начиная с CatBoost 1.2.1 доступны режимы DCG/NDCG/MRR/ERR/MAP. Параметр `top` работает только вне Classic; эти режимы поддерживаются только на CPU. `RecallAt` доступна для измерения, но не как оптимизируемая функция. [Документация CatBoost](https://catboost.ai/docs/en/concepts/loss-functions-ranking).

**Вывод для эксперимента:** сравнить текущую модель с `YetiRank:mode=NDCG;top=50` при фиксированных кандидатах/признаках; победителя выбирать по внешнему Recall@50. NDCG@50 тоже учитывает порядок внутри первой пятидесятки, поэтому совпадения целей нет. Замена одной лишь `eval_metric` не превращает loss в Recall.

По аудиту основной ветки исследования, у 2355 из 2452 dev-запросов один positive: здесь Recall@50 проверяет попадание в первые 50, независимо от точного места. Поэтому смена цели — ограниченный эксперимент, без предположения о крупном приросте.

**Особенность проверки:** встроенный Recall делит число найденных positives на число positives в переданной группе. Если в validation Pool есть только кандидаты, отсутствующие в пуле релевантные документы не войдут в знаменатель. Поэтому встроенная метрика не заменяет полный evaluator проекта. Это следствие формулы [RecallAt](https://catboost.ai/docs/en/concepts/loss-functions-ranking#RecallAt).

Удаление групп без retrieved positive при фиксированном пуле само по себе преимущественно меняет постоянный масштаб среднего и не доказывает причину нестабильного early stopping. Для запросов с несколькими positives дополнительно меняется относительный вес из-за разных знаменателей.

## 2. Добавить семантику пары query–item

`BAAI/bge-reranker-v2-m3` принимает запрос и документ совместно и выдаёт relevance score. Авторская карточка относит модель к multilingual и рекомендует её для мультиязычного использования. В отличие от неё, старые `bge-reranker-base/large` описаны как Chinese/English. Пример использует `AutoModelForSequenceClassification` и пары текстов; `normalize=True` применяет sigmoid. Это не доказывает калибровку вероятности релевантности. [Карточка BAAI](https://huggingface.co/BAAI/bge-reranker-v2-m3).

**Вывод для эксперимента:** один фиксированный мультиязычный cross-encoder оценить на уже доступных кандидатах, сначала как дополнительный признак CatBoost. Сравнить с самостоятельной сортировкой по его score. Начать с умеренной глубины, затем измерить потерю доступных positives из-за усечения. Модель не вернёт документы, отсутствующие среди оцениваемых кандидатов. На русских услугах качество и стоимость требуют собственного замера; карточка не подтверждает достижение 0.9.

При этом сохранить географию и прочие признаки CatBoost: текстовая релевантность не определяет, с каким из одинаково подходящих исполнителей пользователь свяжется. Если обучается отдельная ступень на top-N первой модели, формировать её обучающие кандидаты вне фолда обучения первой модели (OOF), чтобы не получать искусственно лёгкий train. Это вывод о дизайне эксперимента, а не характеристика BGE.

## 3. Fine-tuning E5: сначала корректные negatives

Для asymmetric retrieval E5 требует английские префиксы `query: ` и `passage: ` даже у русских текстов. Авторский пример использует mean pooling по непустым токенам, нормализацию и усечение до 512 токенов. Это полезный предварительный аудит, но не основание менять уже корректную реализацию. [Карточка multilingual-e5-base](https://huggingface.co/intfloat/multilingual-e5-base).

Контрастивное дообучение с hard negatives может усилить шум ложных отрицательных примеров; такой эффект и способы его уменьшения исследуются непосредственно в работе [Wang et al., 2024](https://arxiv.org/abs/2401.00165). `MultipleNegativesRankingLoss` использует другие документы батча как negatives; документация рекомендует `NO_DUPLICATES`, чтобы исключить точные дубликаты. [Sentence Transformers: losses](https://www.sbert.net/docs/package_reference/sentence_transformer/losses.html#sentence_transformers.losses.MultipleNegativesRankingLoss).

**Вывод для данных услуг:** отсутствие контакта не считать доказанным отсутствием релевантности. Исключать известные positives для того же запроса и дубликаты, не класть разные positives одного query в конфликтующие позиции батча. `NO_DUPLICATES` не решает проблему семантически эквивалентных объявлений с разными текстами. Начать с negatives от BM25 и E5, проверять самые похожие; возможен отбор через cross-encoder и margin относительно positive. Эти механизмы реализованы в [официальном mine_hard_negatives](https://www.sbert.net/docs/package_reference/util/hard_negatives.html). Конкретный margin выбирать на своих данных, не переносить число из примера как универсальное.

## 4. Не принять подбор под dev за улучшение

Оптимизация гиперпараметров по конечной validation-выборке способна переобучить сам критерий выбора модели и завысить оценку победителя. Эффект относится и к сравнению многих вариантов/признаков, а не только к обучению весов. [Cawley & Talbot, JMLR 2010](https://www.jmlr.org/beta/papers/v11/cawley10a.html). Инициализация и порядок обучающих примеров также влияют на fine-tuning; это отдельный источник разброса. [Dodge et al., 2020](https://arxiv.org/abs/2002.06305).

**Предлагаемый протокол:** заранее ограничить набор гипотез; для финалистов проверить несколько training seeds при одном split и отдельно перенос на другой split. Seed обучения и seed разбиения отвечают на разные вопросы. Сравнивать paired deltas по одинаковым query, показывать среднее и разброс; для оценки неопределённости ресэмплировать запросы, а не query–item строки. Зафиксировать отдельный holdout, который не участвует в выборе. При повторяющихся query сравнить общую метрику и срез запросов, не встречавшихся в обучающей истории. Это рекомендации для текущей постановки, а не численный результат цитируемых работ.

Порядок по стоимости проверки: аудит evaluator/валидации → небольшой CPU-эксперимент с loss → ограниченный cross-encoder-признак → дообучение E5 после проверки negatives. Каждый следующий шаг оправдан измеряемой ошибкой предыдущего этапа; ни один источник не обещает переход от 0.873 к >0.9.
